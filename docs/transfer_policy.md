# Start point

这是你开发自定义策略的起点。请修改此`./smart_buildings/baselines/transfer_policy.py`。

这是提交策略所使用的模板。默认情况下，它在每个时间步都返回零动作（zero action）。
虽然这是一个合法动作，但它并不是一个好的控制器，因为它实际上没有执行有效的控制。

提供这个模板有两个目的：

1. 确保 `uv run python -m smart_buildings.evaluate` 可以直接运行。
2. 提供一个可以直接修改的策略框架，而不是让你从空文件开始编写。

运行方式：

```bash
uv run python -m smart_buildings.evaluate --policies transfer \
    --buildings building_train_1 --weathers fairbanks_1
```

一个策略只需要实现两个部分：

- `__init__(building_meta_data, action_spec)`：初始化策略。
- `get_action(obs)`：根据观测生成动作。

除此之外，没有其他强制要求：

- 不需要继承任何基类。
- 不需要额外注册策略。
- 如果修改了策略类名，则需要同步更新 `evaluate.py` 中的 `POLICY_MAP`。

## Action Space

动作空间是**混合动作空间（Hybrid Action Space）**，其维度取决于建筑结构。

假设一栋建筑包含：

- `K` 个空气处理机组（Air Handling Unit，AHU）。
- `V` 个变风量末端装置（Variable Air Volume，VAV），每个区域对应一个 VAV。

则动作结构如下：

| 动作                | 数据类型  | 形状             | 含义                                                                      |
| ------------------- | --------- | ---------------- | ------------------------------------------------------------------------- |
| `discrete_action`   | `int32`   | `(K + 1,)`       | 每个 AHU 的开关状态，以及一个水泵开关                                     |
| `continuous_action` | `float32` | `(3K + 2 + 2V,)` | 每个 AHU 的 3 个设定值、热水系统的 2 个设定值，以及每个 VAV 的 2 个设定值 |

连续动作被归一化到 `[-1, 1]`，环境会将其映射到对应的物理单位。

离散动作只能取 `{0, 1}`。

### 连续动作的排列方式

**连续动作采用交错排列（Interleaved Layout），而不是按照控制变量类型分组排列。**

例如，AHU 部分的排列方式为：

```python
[
    temp_0,
    pressure_0,
    recirculation_0,
    temp_1,
    pressure_1,
    recirculation_1,
    ...
]
```

随后依次追加：

1. 热水系统的两个控制量。
2. 各个区域的控制量。

不要假设动作索引的顺序固定，而应该读取 `building_meta_data` 中的以下字段：

```python
building_meta_data["temp_indices"]
building_meta_data["pressure_indices"]
building_meta_data["recirculation_indices"]
building_meta_data["water_indices"]
building_meta_data["zone_action_indices"]
```

然后根据这些索引，将动作值填入连续动作向量的对应位置。

如果在策略中硬编码动作排列方式，程序可能看起来运行正常，但实际上可能一直在控制错误的执行器。

### AHU 与 VAV 的索引关系

前四个索引字段都是按照 AHU 顺序排列的位置列表。

但是，`zone_action_indices` 不同。

它使用映射关系：

- 键：VAV 的 ID，例如 `"VAV_7"`。
- 值：该 VAV 的控制量名称及其对应的动作索引。

原因是每个区域的控制决策都对应某个特定的 VAV，而不能简单依靠数组中的顺序来确定。

此外：

```python
building_meta_data["ahu_zone_assignments"]
```

该字段描述每个 AHU 负责哪些区域，区域采用 `room_N` 的命名方式。

对应的 VAV 命名为 `VAV_N`。

例如，`room_7` 对应 `VAV_7`。

## 连续控制变量的物理含义

### AHU（空气处理机组）

每个 AHU 包含三个控制变量。

| 控制变量                               | 作用                                             |
| -------------------------------------- | ------------------------------------------------ |
| Supply Air Temperature（送风温度）     | 控制进入各区域的空气温度                         |
| Supply Air Static Pressure（送风静压） | 控制风机推动空气的压力，从而影响空气流量         |
| Recirculation（空气再循环比例）        | 控制回风重复利用的比例，而不是全部从室外引入新风 |

### VAV（变风量末端装置）

每个 VAV 对应一个区域，包含两个控制变量。

| 控制变量                      | 作用                                             |
| ----------------------------- | ------------------------------------------------ |
| Supply Air Damper（送风风阀） | 控制该区域获得的送风量                           |
| Reheat Valve（再热阀）        | 控制流入该区域加热盘管的热水量，以加热过冷的送风 |

### 热水系统（Hot-Water System）

热水系统包含两个控制变量。

| 控制变量                             | 作用                                   |
| ------------------------------------ | -------------------------------------- |
| Supply Water Temperature（供水温度） | 控制供热循环系统中的热水温度           |
| Differential Pressure（压差）        | 控制水泵推动热水在循环管路中流动的压力 |

### 空气系统与热水系统的关系

空气系统能够快速改变区域温度。

热水系统决定空气系统可以使用多少加热能力。

一个 AHU 会为其负责的所有区域提供相同的送风温度。

因此，**只有各区域的风阀和再热阀能够实现针对单个区域的独立控制。**

相比项目自带的基线控制器，进一步提升控制性能的主要空间也集中在这里。

## 空调系统的重要物理约束

### AHU 只能制冷，不能加热

**空气处理机组（AHU）只能制冷。建筑中的所有加热都由 VAV 再热盘管完成，而再热盘管的热量来自热水循环系统。**

AHU 首先将回风和室外空气混合，然后将混合空气冷却到指定的设定温度。

因此，实际送风温度为：

`实际送风温度 = min(混合空气温度, 设定送风温度)`

即：

$$
T_{\text{supply}}=\min(T_{\text{mixed}},T_{\text{setpoint}})
$$

在调整送风温度动作之前，必须理解这个公式。

因为当混合空气的温度已经低于允许设定的最低送风温度时，无论如何调整设定值，动作都不会产生实际效果。

而这种情况并不少见。

### 送风温度动作什么时候失效？

混合空气温度计算公式：

$$
T_{\text{mixed}}=rT_{\text{return}}+(1-r)T_{\text{outside}}
$$

其中：

- `r`：回风再循环比例，最大为 `0.70`。
- `T_return`：回风温度。
- `T_outside`：室外空气温度。

已知：

- 再循环比例最大为 `0.70`。
- 最低允许设定送风温度为 `285 K`。
- 当建筑室内温度处于舒适范围时，回风温度约为 `293 K`。

因此，当室外温度低于 **-6.8°C** 时，无论如何设置送风温度，该设定值都不会产生作用。

在项目提供的天气数据中，各气象站在评分时间窗口内的情况如下：

| 气象站    | 室外温度范围  | 送风温度设定值失效的时间比例 |
| --------- | ------------- | ---------------------------- |
| Singapore | 22.9～34.0°C  | 0.0%                         |
| Phoenix   | 0.4～45.6°C   | 0.0%                         |
| Atlanta   | -3.9～35.0°C  | 0.0%                         |
| Denver    | -21.1～37.2°C | 3.8%                         |
| Fairbanks | -42.0～28.9°C | 31.5%                        |

因此：

- **寒冷环境**：真正有效的控制变量主要是热水温度和 VAV 再热阀，送风温度设定值在很多时候几乎不起作用。
- **炎热环境**：送风温度是最重要的控制变量之一。

这是建筑物理系统本身的特性。

这里明确指出这一点，是为了避免你必须通过消融实验才能发现这个问题。

### 通风下限由模拟器强制执行

**通风下限由模拟器自动执行，而不是由策略负责保证。**

当 AHU 处于运行状态时，模拟器会施加以下限制：

1. AHU 必须维持最低静压。
2. 空气再循环比例不能超过 `70%`。
3. 每个 VAV 风阀的开度不能低于 `10%`。

如果策略给出的动作低于这些下限，不会触发错误。

模拟器只会直接使用允许的最低值。

由于有人使用的区域必须持续获得室外新风，因此不能通过关闭所有通风设备来节约能源。

## Observation Space

观测是一个一维浮点向量（Flat Float Vector）。

向量长度取决于建筑结构，例如：

- `building_train_1`：352 维。
- `building_train_8`：271 维。

可以通过以下字段获取每个观测元素对应的名称：

```python
building_meta_data["observation_field_names"]
```

建议在 `__init__` 中建立一次名称到索引的映射表，然后利用该映射提取观测。

不要直接假设某个变量始终位于固定的索引位置。

### 每个区域的观测

- 区域空气温度。
- 当前供暖温度设定值。
- 当前制冷温度设定值。
- 风阀开度。
- 再热阀开度。
- 空气流量设定值。

### 每个 AHU 的观测

- 实际送风温度。
- 送风温度设定值。
- 实际静压。
- 静压设定值。
- 实际空气流量。
- 空气流量设定值。
- 室外空气温度。
- 空气再循环比例。
- 制冷请求数量。
- 风机运行状态。

### 其他观测信息

- 热水系统状态。
- 建筑人员占用情况。
- 舒适度时间表标志。
- 一天中的时间（周期编码）。
- 一周中的日期（周期编码）。

### 实际执行动作与命令动作不同

观测中的风阀开度和再热阀位置，反映的是设备**实际执行的状态**，而不一定是策略请求的值。

例如，如果策略要求风阀开度低于最低通风要求，模拟器会将其限制到最低允许开度。

下一步观测返回的也是这个实际执行的开度。

### 无法直接获取天气和建筑身份

**观测中不包含以下信息：**

- 天气类别标签。
- 月份。
- 气象站名称。
- 建筑 ID。

策略必须通过以下信息推断当前气候条件：

- `outside_air_temperature_sensor`。
- 当前建筑状态。
- 一天中的时间。

这是比赛有意设置的限制。

根据比赛规则，硬编码对隐藏测试配置或天气随机种子的引用，会导致参赛资格被取消。

## Evaluation

每个时间步的评分由三个目标加权组成：

| 目标                           | 权重 |
| ------------------------------ | ---- |
| 人员舒适度（Occupant Comfort） | 0.6  |
| 能源成本（Energy Cost）        | 0.2  |
| 碳排放（Carbon Emissions）     | 0.2  |

这是一个多目标权衡问题。

### 舒适度惩罚

舒适度根据室内温度是否处于允许的温度区间来判断。

在非舒适时段，允许的温度区间会变宽。

需要特别注意：

**舒适度惩罚没有上界（Unbounded Penalty）。**

当某个区域的温度偏离允许区间超过 `5 K` 时，惩罚会以二次函数形式增长。

因此，一个长期没有得到有效控制、温度严重偏离舒适区间的区域，就可能主导整个 episode 的评分。

### 零动作并不意味着关闭系统

什么都不做并不安全。

此外，零动作（Zero Action）也不等于完全不控制。

因为连续动作被归一化到 `[-1, 1]`：

- `-1`：对应物理控制范围的下限。
- `0`：对应物理控制范围的中间值。
- `1`：对应物理控制范围的上限。

因此，如果直接使用模板中默认的零动作，相当于：

- 每个风阀都打开到控制范围的中间位置。
- 每个再热阀都处于控制范围的中间位置。

并不是将所有设备关闭。

### Baselines

可以参考同一目录下提供的基线控制器。

用于定义评分基准的四个控制器是：

1. `bang_bang`
2. `fixed_setpoint`
3. `pid`
4. `pid_water`

其中，两个表现较弱的控制器在不同气候条件下存在相反的问题：

- `bang_bang`：在寒冷环境下，是四个控制器中表现最差的。
- `fixed_setpoint`：在炎热环境下，是四个控制器中表现最差的。

因此，评分尺度的下限并不是根据某个控制器在单一环境中的糟糕表现确定的。

一个能够在所有环境中超过基准下限的策略，必须同时具备良好的寒冷环境和炎热环境控制能力。

此外，`all_off` 控制器也可以运行。

它用于帮助理解真正关闭建筑设备会产生多大的代价，但不属于定义评分尺度的四个基线控制器。
